**桐谷**：杏奈さんに同意です。ただし形式 A 単独では足りない。**形式 A をベースに、F3.1 アルゴリズム仕様だけは Stage 2 §4.1 に「§4.1A 統合アルゴリズム」サブセクションを切る** ハイブリッド案 (A+) を提案します：

## Turn 4｜制約と法則 — 整合性ガードの設計

**桐谷**：要件書アップデートで最も気をつけるべき **制約 3 件**：

**制約 ①: Constitution-as-Code との二重定義禁止**

```typescript
// lib/constitution/three-layer-model.ts は単一の真実
export const HYBRID_DISTANCE_ALPHA = { layer1ToLayer2: 0.7, layer2ToLayer3: 0.3 }
```

要件書に「Layer 1→2 の α = 0.7」と数値を **直接書くと、Constitution との drift リスク** が発生する。要件書では `HYBRID_DISTANCE_ALPHA.layer1ToLayer2` と **シンボル参照** で記述し、数値の真実は Constitution に委ねる。**「Constitution が値、要件書がポインタ」**。

**制約 ②: 既存 D1〜D10 との時系列整合性**

D1〜D10 は 2026-05-24 / 2026-05-25 に確定済み。D11+ を追記する際、

- **既存 D を編集しない** (履歴を消さない — Anatta-Aware の精神)
- D11 の本文で **D10 (60type 採用) との関係を明示** (「D10 の 60type データを Q5b twigs として再活用」)
- 矛盾する場合は **D11 で D10 を「上書き」と明記**

**制約 ③: Stage 1 / Stage 2 の役割分離**

Stage 1 = **What/Why** (機能要件・優先度・KPI)
Stage 2 = **How** (業務フロー・例外系・インテグレーション)

新規 §4.1A (アルゴリズム仕様) は Stage 2 に置き、Stage 1 には「F3.1.11 で harvest 関数を呼ぶ」とだけ書く。Stage 1 に harvest の実装詳細を書くと **Stage 2 と内容が重複し、変更管理コストが倍** になる。

**杏奈**：制約 ① への補足として、**Anatta-Aware Output ガードも同じパターン** にすべき：

```typescript
// lib/constitution/banned-output-patterns.ts (新設予定)
export const BANNED_OUTPUT_PATTERNS = [
  /あなたは(.{1,30})です/,           // 断定
  /あなたは(.{1,30})タイプです/,      // タイプ断定
  /必ず(.{1,30})する/,              // 不可逆断定
] as const
```

要件書 (Stage 1 非機能要件) では「`lib/constitution/banned-output-patterns.ts` で機械検出」とだけ書き、正規表現の実体はコード側に置く。これにより、**禁止構文の追加更新が要件書を巻き込まずに済む**。

**桐谷**：両者を **法則化** すると、要件書アップデートを支配する 3 法則：

> 🟡 **Turn 4 法則**:
> ① **Constitution Holds Values, Spec Holds Pointers.** — 数値・正規表現は Constitution、要件書はシンボル参照
> ② **Append, Don't Overwrite (Decisions Log).** — 既存 D を編集せず、D11+ で文脈を追加
> ③ **Stage 1 = What/Why, Stage 2 = How.** — 役割分離で変更管理コスト最小化

**みさき**：これ全部、**「要件書も Constitution として扱う」** って話ですよね〜？ なんか哲学っぽくてかっこいい〜。でも素朴な疑問なんですけど、**Phase 1 リリースに間に合うんですか?** いま私たちこの議論してる時間、実装した方が良くないですか〜？

**桐谷**：みさきさん、現実的な突っ込みです。私の見立てでは、

| 作業 | 工数 |
|---|---|
| Stage 1 v1.2 改訂 (F3.1.11〜15 + D11〜13 + 非機能要件 1 件) | 2 時間 |
| Stage 2 v1.2 改訂 (§4.1A / §4.1B + リスク 1 件 + 変更管理ログ) | 3 時間 |
| `banned-output-patterns.ts` 新設 (要件書反映のみ、実装は Phase 1 内) | 30 分 |
| 議論ログ保存 + commit | 30 分 |

合計 **6 時間 = 1 営業日**。Phase 1 着手前 (=今週末) に完了可能で、**実装本走に遅延を発生させずに済む**。さらに重要なのは、要件書を 1 日かけて整備することで、**Phase 1 実装中に「これ要件にあったっけ?」の往復問い合わせがほぼ消える**こと。投資としては圧倒的に元が取れます。
