# COCOSiL V2 — F3 統合レポート 詳細要件定義書

> **4体系を1つの立体的な自己像として届ける**
> UXシーケンス「安心 → 分析」の中核実装。V2の核心フィーチャー。

---

## 1. プロジェクト概要

F3「統合レポート」は、COCOSiL V2の全体体験において「安心 → 分析」フェーズを担う中核フィーチャー群である。F2で収集した4体系診断データ（星座・動物性格診断・六星占術・MBTI）をAIが統合し、東洋哲学のパンチャ構造（4+1=5）に基づいた「1つの立体的な自己像（識）」をユーザーに届ける。バラバラの「ラベル集」ではなく、「なぜ自分はこうなのか」が構造として腑落ちする体験の生成が目的である。

技術実装は3層で構成される。**生成層**：OpenAI（GPT-4o系）が4体系を統合したレポートコンテンツをLLMで生成する。**整形層**：Vercel OG（Satori）がサーバーサイドで縦長（1024×1792）の構造化レポートを即時生成し文字崩れゼロを保証する。Phase 3以降でgpt-image-2（OpenAI）を背景・アイコン専用として追加する。**体験層**：レポート表示直前に「安心（F3.2）」フェーズを必ず挿入し、「結果＝評価」から「結果＝地図」への認知転換を保証する。

5サブフィーチャーはPhase 1（F3.1〜F3.4：初回体験MVP）とPhase 3（F3.5：継続課金体験）に段階分割して実装する。

## 2. ビジネス要件

### 2.1 対象課題（F3固有の視点）

| 課題 | F3との対応 |
|------|-----------|
| **4ラベルの断片化**：MBTI/星座/動物/六星を個別に知っていても「なぜ自分はこうなのか」の構造的理解に至らない | F3.1の「+1の統合」考察セクション（AC-1）が解消する |
| **判定不安**：診断結果を「評価・ジャッジ」として受け取り、結果表示直前に防衛的になる（タップ速度37%低下） | F3.2「安心」フェーズの「地図」メタファーが解消する |
| **診断で終わる**：読んで「ふーん」で終わり行動変容に繋がらない | F3.3マーカー（気づきの記録）→F4/F5への継承で解消する |
| **継続性の欠如**：1回の診断では自分の変化が見えず、継続利用の動機がない | F3.5の蓄積データ反映型再生成（D3）が解消する |

### 2.2 提供価値（F3が担う UVP）

> **「4つのラベルがバラバラだったあなたへ。これが、あなたという人の全体図だ。」**

F3が届けるのは単なる診断結果の表示ではなく、**「なぜ自分はこうなのか」が腑落ちする構造的な自己理解**である。設計中枢 原則①（Dispel, Don't Decorate）に従い、エンタメ的な飾り付けより自己理解の解像度向上を優先する。

### 2.3 競合優位性（7Powers — F3に関連するPower）

| Power | F3への適用 |
|-------|-----------|
| **Cornered Resource（独占資源）** | 4体系統合ナレッジ（特に動物占い60アニマル×六星占術×MBTI）の構造化とAI推論基盤への統合は業界最先端。えんまさが設計する「地図」メタファーを使った安心プロンプト体系は容易に模倣できない |
| **Switching Costs（スイッチングコスト）** | F3.3マーカーの蓄積・F3.5の継続的な再生成により「自分の自己理解の旅路」がCOCOSiLに刻まれていく。他サービスに移行すると蓄積がゼロリセットされるコストが発生する |
| **Counter-Positioning（カウンターポジショニング）** | 既存の診断系（16Personalities等）がレポートを静的コンテンツとして提供するのに対し、COCOSiLは「安心フェーズ」「マーカー記録」「蓄積型再生成」で**生きた地図として育てる**設計。既存プレイヤーがこれを模倣すると自社の「シンプルな診断ツール」というポジションが崩れる |

### 2.4 KGI / KPI（F3直接関連）

| 指標 | 目標値 | 計測方法 | 計測開始 |
|------|--------|---------|---------|
| **レポート満足度** | **4.0/5.0以上** | F3.4アンケート回答（`analytics_events`） | Phase 1リリース初日 |
| **しっくりきたマーカー利用率** | **10%以上** | F3.3マーカータップ数 / レポート表示数 | Phase 2で検証（Phase 1でデータ蓄積） |
| **7日以内再訪率** | **30%以上** | Supabase analytics_events | Phase 1リリース後（F3はコア体験の一部） |

## 3. ユーザー要件

### 3.1 ターゲットユーザー

| セグメント | 属性 | F3との接点 |
|-----------|------|-----------|
| **プライマリー** | 25〜35歳・若手社会人 | F3.1〜F3.4の中心ユーザー。初回体験でレポートを受け取り、マーカーや満足度アンケートを使う |
| **アーリーアダプター** | MBTIオタク・自己分析SNS投稿層 | F3.3マーカーで「気づき」を記録し、シェアカード（F6）に繋げる |
| **継続課金ユーザー** | 1ヶ月以上使い込んだユーザー | F3.5の再生成ターゲット。自分の変化を「今の地図」で確かめたい層 |

### 3.2 ペルソナ

#### ペルソナA: 佐藤 麻衣（F3.1〜F3.4の中心ペルソナ）

- **属性**: 28歳・都内IT企業のCSマネージャー・年収420万円
- **行動パターン**: MBTIをSNSで定期投稿。ストレングスファインダーも受けたことがある。夜、仕事のモヤモヤをTwitterに書いてしまいがち
- **課題**: チームメンバーとの関係でいつも同じパターンで消耗する。「なぜ自分はこうなのか」が分からない
- **判定不安の強さ**: MBTI好きゆえに「タイプ判定」への意識が高く、診断結果遷移直前の「無防備ゾーン」が特に顕著（タップ速度37%低下）
- **F3への期待**: 「占い」とは言いたくないが、4つの体系を合わせた「これが私の全体像だ」という体験をしたい。AIに「そうそう、それなんだよ」と言いたい
- **F3の体験ゴール**: レポートを「評価される」ではなく「一緒に読む地図」として受け取れる状態でF3.1に辿り着く

#### ペルソナB: 田中 健太（F3.5の中心ペルソナ）

- **属性**: 31歳・スタートアップ勤務のエンジニア・年収550万円
- **行動パターン**: 週1回自己分析ツールを使う。Notionに気づきを記録している。「なぜ自分はこう行動するのか」に強い関心
- **課題**: 単発の診断では行動が変わらない。「分析で終わる」体験に飽き飽きしている
- **F3.5への期待**: 「1ヶ月使ってきた記録が次のレポートに反映される」という継続利用の価値を感じたい。「前回よりも解像度が上がった」という変化の実感が欲しい
- **F3の体験ゴール**: 1ヶ月分の蓄積が織り込まれた更新版レポートを受け取り「今の自分の地図」を手に入れる

### 3.3 MVPの体験定義（ユーザー視点）

**F3 Phase 1 MVPを使うと、ユーザーは何ができるか：**

> 4体系診断（F2）を完了した麻衣が、「安心」フェーズ（F3.2）で判定不安を和らげ、4体系を統合した縦長レポート（F3.1）を受け取り、「これ自分だ」と感じたセクションをワンタップで記録し（F3.3）、読み終えたら5段階で感想を送れる（F3.4）。この一連の流れが登録初日に体験できる。

**F3 Phase 3 MVPを使うと（F3.5）：**

> 1ヶ月以上COCOSiLを使ってきた田中（課金ユーザー）が、前回生成から30日経過後に再生成ボタンを押すと、1ヶ月分のチャット・マーカー・アクション記録が反映された「今の自分の地図」を受け取れる。

## 4. 機能要件詳細

> Stage 1 の機能要件（F3.1〜F3.5）を業務フロー（正常系・例外系）と特殊要件で詳細化。

### 4.1 F3.1 レポート生成エンジン

**概要**: F2の4体系診断データをOpenAI APIで統合したレポートコンテンツを生成し、Vercel OG（Satori）で縦長（1024×1792）の構造化レポートとしてサーバーサイドで即時整形・表示する。Supabase Storageに永続化し、F3.2〜F3.4の土台となる。

**対応Stage 1要件**: F3.1.1〜F3.1.7

**業務フロー（正常系）**:

1. MBTI診断完了（またはスキップ確定）を検知し、**バックグラウンドでLLM生成を開始**する（POST `/api/reports/generate`）
2. Clerk JWT → `supabase.auth.getUser()` でユーザー特定。Zodスキーマで入力値（4体系データ・`user_id`）を全検証
3. OpenAI API（30秒タイムアウト）に4体系データを送信し、レポートコンテンツを生成
   - 必須セクション：4体系横断統合考察（1セクション以上）、「大切な人との関係ヒント」（1セクション以上）
   - プロンプトはえんまさ設計（`lib/prompts/report/system-prompt.ts`）、Gate 2対象
4. 生成済みコンテンツを `og-image.tsx`（Reactコンポーネント）に流し込み、`@vercel/og` で **1024×1792 PNG** を生成
5. Supabase Storage `user-reports` バケットに `${user_id}/${uuid}.png` で保存（RLS policy: `user_id = auth.uid()`）
6. レポートURL（Storage公開URL）をレスポンスとして返す
7. F3.2「安心」フェーズのCTAタップ or 15秒経過後、レポート本体を表示

**例外系**:

| 状況 | 挙動 |
|------|------|
| OpenAI API タイムアウト（30秒超過） | 「少し時間がかかっています。もう一度試してみてください」（言語設計準拠）のフレンドリーエラー＋リトライボタン表示。エラーオブジェクトをそのままクライアントに返さない |
| OpenAI API 障害（5xx等） | 同上。最大3回リトライ後、Markdown+CSS 静的フォールバックへ切替 |
| Vercel OG 生成失敗 | Markdown+CSS 静的レポートにフォールバック。ユーザーに生成失敗を悟らせない（フォールバック表示とリッチ表示の体験差を最小化） |
| Supabase Storage 保存失敗 | 表示は成功させ、保存リトライをバックグラウンドで行う。保存失敗ログを記録 |
| 入力値バリデーション失敗（Zodエラー） | 400エラーと共に具体的なフィールドエラーをクライアントに返す（内部エラーは含まない） |

**特殊要件**:

- プロンプトファイル（`lib/prompts/report/`）の変更はGate 2（えんまさ承認）必須。AI応答サンプル3件（before/after）の添付が必要
- `lib/constitution/banned-words.ts` による禁止語ユニットテストをCI必須化
- **F3.1は初回生成のみ担当**。再生成（30日ゲート・課金ゲート・蓄積データ反映）は F3.5（TSK-API-009）で実装
- gpt-image-2による背景・アイコン画像生成はPhase 3以降。文字レイヤーは全フェーズVercel OGが担保

### 4.2 F3.2「安心」フェーズ

**概要**: F3.1レポート生成完了後・表示直前に**スキップ不可**で挿入される15秒以内の儀式。「結果＝評価」から「結果＝地図」への認知転換（Receptive状態化）を保証する。設計三原則（Zero-Effort Reassurance / Active→Receptive Handoff / De-judging through Metaphor）に基づく。

**対応Stage 1要件**: F3.2.1〜F3.2.8

**業務フロー（正常系 — 初回）**:

1. F3.1のレポート生成を検知（または並行生成中）して**即座にF3.2画面へ遷移**（生成と並行）
2. **呼吸アニメーション**（CSS、4〜8秒）を全画面で開始
3. 固定テキストを表示：「あなたの結果が揃いました。読む前に、ひとつだけ。」（60字以内）
4. **AIサブテキスト**を表示（承認・脱判定化・招待の3要素・100字以内・「地図」メタファー）
5. CTA「読んでみる→」（Thumb Zone内）を表示
6. CTAタップ **または** 15秒経過の自動遷移 → レポート本体（F3.1）へ遷移

**業務フロー（正常系 — 再訪時）**:

1. F3.1の再表示 or F3.5の再生成完了後に F3.2 を挿入
2. アニメーションを短縮版（2〜3秒）で表示
3. 固定テキストを再訪用テキストに変更（えんまさ設計）
4. CTA または 10秒経過後にレポートへ遷移

**例外系**:

| 状況 | 挙動 |
|------|------|
| F3.1生成がF3.2（15秒）より長くかかる（並行生成） | F3.2を最大30秒に延長。30秒経過後にローディングインジケーター表示。生成完了後即時遷移 |
| ユーザーが15秒前にブラウザを閉じた | セッション保持（30分以内は状態復元）。戻ってきた場合F3.2を再挿入 |
| AIサブテキスト生成失敗 | フォールバックの固定サブテキスト（えんまさ事前設計・`lib/prompts/report/reassurance-subtext.ts`に格納）を表示。F3.2の表示は必ず完了させる |

**特殊要件**:

- **スキップ不可はコードレベルで保証**する。スキップボタン・設定・オプトアウト導線を一切設けない（設計中枢 原則②・`lib/constitution/ux-sequence.ts` の非交渉ルール）
- テキスト入力・選択肢・スワイプなし。インタラクションはCTAボタン1つのみ（F1.3 Active モードとの明確分離）
- AIサブテキストの**プロンプト設計はえんまさ（Gate 2対象）**。「地図」メタファー・承認・脱判定化・招待の3要素を100字以内で含むことをユニットテストで保証
- 禁止語（占い・鑑定・当たる・霊感・霊視）0%を `lib/constitution/banned-words.ts` でCIチェック

### 4.3 F3.3「しっくりきた」マーカー

**概要**: レポート閲覧中、「これ自分だ」と感じたセクションをワンタップで記録する機能。止観の「観（=パターンの命名）」の最小ユーザーアクション。記録は F4.3（過去気づき参照）・F5.3（振り返り）に継承される。

**対応Stage 1要件**: F3.3.1〜F3.3.5

**業務フロー（正常系）**:

1. ユーザーがレポートを読み進める中で特定のセクションに「これ自分だ」と感じる
2. そのセクションに配置された「しっくりきた」マーカーボタンを**1タップ**
3. タップ瞬間に視覚フィードバック（チェックマーク表示・色変化）が**100ms以内**に返る
4. `know_markers` テーブル（仮称）にセクションID・マークテキスト・タイムスタンプ・`user_id` を保存
5. 同セクションを再タップ → **マーク解除**（1タップで可逆）。DB レコードを削除またはフラグ変更
6. レポートから離脱後も記録は永続化。F4チャット画面やF5振り返りで参照可能

**業務フロー（F4.3への継承 — 参照側）**:

1. F4チャットのPhase 4（洞察）フェーズで、AIが過去のマーカーデータをコンテキストに含む
2. 「先日のレポートで〇〇のところに『しっくりきた』とマークされていましたね」のトーンで参照

**例外系**:

| 状況 | 挙動 |
|------|------|
| DBへの保存失敗 | ローカルで楽観的更新（UI上はマーク済み表示）。バックグラウンドでリトライ。失敗した場合は画面リフレッシュ後に未マーク状態に戻る |
| マーカーが0件 | 「まだマークがありません」等の否定形表示を一切出さない。空状態は無表示かデザイン上のニュートラル表現のみ |
| ネットワーク切断中のタップ | オフライン保留キューに記録し、オンライン復帰後に自動送信 |

**特殊要件**:

- **UIテキスト（チェックラベル・ボタン文言等）はえんまさ設計（Gate 2対象）**
- マーカーデータのRLSポリシー：`user_id = auth.uid()` を必ず適用（Gate 1チェック必須）
- マーク数の集計表示・ゲーミフィケーション（「○個マーク！」）は設計中枢 原則②（三毒増幅禁止）により**永久に入れない**
- マーカーのF4チャットへの注入処理（プロンプトへの組み込み）は **F4.3の責務**。F3.3は記録と永続化まで

### 4.4 F3.4 満足度アンケート

**概要**: レポート読了直後に5段階評価＋自由記述でユーザーの感想を収集し、PMF基準（レポート満足度4.0/5.0）を計測する。V1継承・必須機能。

**対応Stage 1要件**: F3.4.1〜F3.4.6

**業務フロー（正常系）**:

1. ユーザーがレポートを末尾まで スクロールして読了
2. **レポート末尾に5段階評価UI**が自然に表示される（スクロールで到達・強制表示ではない）
3. 5段階のいずれかを**1タップで選択**（選択と同時に送信）
4. 自由記述欄（任意）が表示され、「ひとこと感想」を任意入力
5. 空欄のままでもスキップボタンで先へ進める
6. 送信後：「ありがとうございます」等の言語設計準拠テキストを表示（否定形・プレッシャーを与える表現なし）
7. 自動的に次アクション導線（F4チャットへの誘導）を表示
8. 回答を `analytics_events`（または専用テーブル）に記録。F9.3 KPIダッシュボードで集計

**例外系**:

| 状況 | 挙動 |
|------|------|
| ユーザーがアンケートをスキップ | 後続機能（F4チャット等）に制限なく進める。スキップを責める表示（「評価してください」等）なし |
| DB保存失敗 | フロントエンドでは成功として扱い、ユーザー体験を中断しない。バックグラウンドでリトライ |
| F3.5再生成後の再閲覧時のアンケート再表示 | 再表示するか非表示にするかは Eval 層で確定（仮定：初回のみ表示、再生成後は7日以上経過したら再表示）(要確認) |

**特殊要件**:

- 送信後・空状態のテキストは **言語設計ルール準拠**（`lib/constitution/banned-words.ts`）。否定形・プレッシャーを与える表現を使わない（Gate 2対象）
- アンケートの強制ゲート化（回答しないと先へ進めない）は**永久に入れない**（設計中枢 原則②）
- 多項目・詳細アンケート（NPS・機能別評価等）はV2スコープ外。5段階＋自由記述のみ

### 4.5 F3.5 レポート再生成

**概要**: 課金プランのユーザーが月1回、前回以降の蓄積データ（F4チャット・F3.3マーカー・F5記録）を反映した更新版レポートを受け取る。「生きた地図」として統合像を育て直す更新ループ。Phase 3実装。

**対応Stage 1要件**: F3.5.1〜F3.5.6

**業務フロー（正常系）**:

1. ユーザーがレポート画面（またはマイページ）の「レポートを更新する」ボタンをタップ
2. **課金状態チェック**：有料プラン確認 → OK → 次へ / NG → 有料誘導表示（AC-2）
3. **30日ゲートチェック**：前回生成から30日以上経過 → OK / 未経過 → ボタン無効 + 次回可能日表示（AC-1）
4. 蓄積データ取得：前回生成以降の F4 チャット履歴・F3.3 マーカー記録・F5 アクション記録を取得
5. POST `/api/reports/regenerate`：蓄積データをコンテキストに注入した再生成プロンプト（`lib/prompts/report/regenerate-prompt.ts`）でLLM生成開始
6. F3.2「安心」フェーズを再挿入（再訪時短縮版）
7. 新しいレポートをVercel OGで整形・Supabase Storageに保存（旧レポートはDB保持・比較UIなし）
8. 月次再生成枠を消費（次回有効化は30日後）

**業務フロー（蓄積データ乏しい場合）**:

1. 前回生成以降の蓄積データが0件または極小（チャット0回・マーカー0件・アクション0件）
2. プロンプトが破綻しないよう、蓄積データなし時のフォールバックプロンプトに切替（`regenerate-prompt.ts` 内分岐）
3. 「今の自分の視点で改めて4体系を見渡した」角度のレポートを生成（初回との微差は保証する）
4. 生成完了後は通常フローと同一

**例外系**:

| 状況 | 挙動 |
|------|------|
| 無料プランからの再生成試行 | レポートを生成せず「有料プランで月1回レポートを更新できます」の誘導を表示（言語設計準拠・禁止語0%） |
| 前回生成から30日未経過 | 再生成ボタンを視覚的に無効化（グレーアウト）。ボタン下部に「次回更新可能日：○月○日」を表示 |
| LLMタイムアウト / API障害 | F3.1と同様のフレンドリーエラー＋リトライ導線。月次再生成枠は消費しない（ロールバック） |
| Supabase Storage保存失敗 | リトライ。失敗しても旧レポートは保持される（データ損失なし） |

**特殊要件**:

- **再生成プロンプト（`lib/prompts/report/regenerate-prompt.ts`）はえんまさ設計（Gate 2対象）**。AI応答サンプル3件（before/after）の添付が必要
- 課金ゲートの実装はF7（Stripe）との連携が前提。`subscription_status` の検証方法はF7仕様に準拠
- 旧レポートの履歴比較UI・差分表示UIは**V2スコープ外**。変化は新しいレポートの内容で伝える
- 月1回を超える再生成（追加課金での即時再生成等）は**V2では入れない**
- F3.5はF3で唯一Phase 3実装。依存解消条件：F7（Stripe課金）実装完了 ＋ F4/F3.3/F5がPhase 1〜2で稼働済み

## 5. 非機能要件

### UI / UX

- スマートフォン優先設計（iOS/Android ブラウザ）。CTA・タップターゲットはThumb Zone（画面下60%）内に配置
- F3.2「安心」フェーズはフルスクリーン表示（コンテキストをシャットアウトし、Receptiveモードに集中させる）
- F3.3マーカーのタップ視覚フィードバックは **100ms以内**（読みながら反射的に付けられる超低摩擦設計の前提）
- 「占い」「鑑定」「当たる」「霊感」「霊視」は全UIテキストで禁止（`lib/constitution/banned-words.ts` がCIで検証）

### パフォーマンス

| 対象 | 目標値 | 根拠 |
|------|--------|------|
| Vercel OGレポート整形 | **3秒以内**（初回表示） | Phase 1〜2：サーバーサイドで即時生成 |
| OpenAI LLM生成タイムアウト | **30秒** | タイムアウト後フレンドリーエラー＋リトライ |
| F3.2合計時間（初回） | **15秒以内**（並行生成時最大30秒） | 15秒超えると摩擦化 |
| マーカータップレスポンス | **100ms以内** | 反射的タップの前提 |

### データ可用性とセキュリティ

- Supabase Storage RLS：`user_id = auth.uid()` を全CRUD操作のRLSポリシーに必ず適用（Gate 1 IDOR防御チェック）
- Clerk JWT連携：`supabase.auth.getUser()` 経由のみ。`request.headers` 直読み禁止
- APIルート入力値：Zod（`zod/v4`）スキーマで全検証。SQLインジェクション防止
- エラーオブジェクトをそのままクライアントに返さない（内部スタックトレース・DB情報の露出禁止）
- Supabase Storage使用量：0.5GB上限（無料枠）内で運用。古いレポートPNGの定期アーカイブ戦略を初日から実装

### 対応環境

- プライマリ：iOS/Android Chrome / Safari（スマートフォン）
- セカンダリ：デスクトップ Chrome / Firefox / Safari
- Vercel OGはサーバーサイドレンダリングのためブラウザ依存なし

## 6. インテグレーション要件

### 6.1 OpenAI API（レポートコンテンツ生成・F3.2サブテキスト生成）

- **用途**: F3.1レポート本文生成、F3.2AIサブテキスト生成、F3.5再生成プロンプト実行
- **連携方式**: Next.js API Route Handler（`app/api/`）から `openai` Node SDK経由で呼び出し。`process.env` 直読み禁止・`@/lib/env` の `getServerEnv()` 経由で環境変数取得
- **認証方式**: API Key（`OPENAI_API_KEY`）。`.env.local` で管理・リポジトリにコミットしない
- **タイムアウト**: 30秒。超過でフレンドリーエラー＋リトライ
- **想定コスト（仮定）**: 初回レポート生成1件あたり $0.01〜$0.05（GPT-4o料金・レポート長による）。月間1,000ユーザー × 平均1.5回生成で $15〜$75/月（仮定）

### 6.2 Vercel OG（Satori）（レポート整形・画像生成）

- **用途**: F3.1・F3.5のレポートコンテンツを縦長（1024×1792）PNG画像に整形
- **連携方式**: `@vercel/og`（Next.js App Routerのimage response）。`app/api/reports/og/route.tsx` にReactコンポーネントベースのOGハンドラを実装
- **認証方式**: Vercel内部サービス（認証不要）
- **想定コスト**: Vercel無料枠内（サーバーレス関数として実行。実行時間が短いため費用ほぼゼロ）

### 6.3 gpt-image-2（OpenAI）— Phase 3以降

- **用途**: F3.1・F3.5レポートの背景・アイコン画像生成（文字レイヤーはVercel OGが担保）
- **連携方式**: `openai` Node SDK の images.generate API
- **実装タイミング**: Phase 3以降。Phase 1〜2はVercel OGのみで完結
- **想定コスト（仮定）**: 1画像あたり $0.04〜$0.08（中品質・1024×1024）。Phase 3で詳細見積もり（要確認）

### 6.4 Supabase PostgreSQL（マーカー・アンケート記録）

- **用途**: F3.3マーカーデータ・F3.4アンケート回答・F3.5月次再生成枠の管理
- **連携方式**: Supabase JS SDK（`@supabase/supabase-js`）。サーバーサイドのみ（API Route Handler内）
- **認証方式**: Clerk JWT → `supabase.auth.getUser()` でユーザー特定。クライアントからの直接書き込みはRLSで制限
- **データ種別**:
  - `know_markers`（仮称）：`user_id`, `report_id`, `section_id`, `section_text`, `created_at`
  - `analytics_events`（既存）：アンケート回答レコード
  - `reports`（仮称）：`user_id`, `storage_url`, `generated_at`, `regen_count`, `last_regen_at`

### 6.5 Supabase Storage（レポート画像永続化）

- **用途**: F3.1・F3.5で生成したレポートPNGの保存
- **バケット名**: `user-reports`
- **パス構造**: `${user_id}/${uuid}.png`
- **RLS policy**: `user_id = auth.uid()` 適用（IDOR防御）
- **ストレージ上限**: 0.5GB（Supabase無料枠）。積極的アーカイブ戦略で管理

### 6.6 Clerk（認証）

- **用途**: F3.1/F3.5のAPIルート内でユーザー認証
- **連携方式**: `auth()` を API Route Handler内で直接呼び出し。Server Actions経由不使用（AGENTS.md §1厳格ルール）
- **認証フロー**: Clerk JWT → `supabase.auth.getUser()` → `user_id` 取得 → RLS適用

### 6.7 Stripe（F3.5課金ゲート）— F7依存

- **用途**: F3.5の再生成ボタン表示時に課金プラン状態を確認
- **連携方式**: F7（Stripe課金機能）が提供する `subscription_status` テーブル/APIを参照
- **実装タイミング**: Phase 3（F7完了後）

## 7. 技術選定とアーキテクチャ

### 7.1 技術スタック（F3固有）

| レイヤー | 技術 | F3での役割 |
|---------|------|-----------|
| レポート整形 | Vercel OG（Satori） | 縦長1024×1792 PNG。サーバーサイド即時生成。文字崩れゼロ |
| ビジュアル生成（Phase 3〜） | gpt-image-2（OpenAI） | 背景・アイコン専用。文字レイヤー非担当 |
| コンテンツ生成AI | OpenAI（GPT-4o系） | 4体系統合レポート本文・安心サブテキスト・再生成 |
| データ永続化（画像） | Supabase Storage | PNGを `user-reports` バケットに保存 |
| データ永続化（構造化データ） | Supabase PostgreSQL | マーカー・アンケート・再生成管理 |
| 認証 | Clerk + Supabase JWT | `supabase.auth.getUser()` でClerk JWTを検証 |
| APIルート | Next.js 16 App Router | `app/api/reports/generate`・`regenerate`・`og` |
| バリデーション | Zod（`zod/v4`） | 全APIルート入力値の検証 |
| フロントエンド | Next.js 16 + Tailwind CSS 4 + TypeScript 5 | F3.2アニメ・F3.3マーカーUI・F3.4アンケートUI |

### 7.2 データフロー

```
[F2診断完了] → POST /api/reports/generate
                  ↓
             Zod バリデーション
                  ↓
         Clerk JWT → supabase.auth.getUser()
                  ↓
             OpenAI API（30秒タイムアウト）
                  ↓ 成功                ↓ 失敗（30秒超・5xx）
         Vercel OG (og-image.tsx)    Markdown+CSS フォールバック
                  ↓
         Supabase Storage user-reports/${user_id}/${uuid}.png
                  ↓
         レポートURL → レスポンス返却
                  ↓
         [F3.2 安心フェーズ UI] ← 並行表示
                  ↓ (CTAタップ or 15秒)
         [F3.1 レポート表示]
                  ↓
         [F3.3 マーカーUI] → Supabase know_markers
                  ↓（末尾スクロール）
         [F3.4 アンケートUI] → Supabase analytics_events
```

### 7.3 アーキテクチャ方針

- **API-Firstの厳守**: F3のビジネスロジック（LLM生成・Storage保存・課金ゲート）はすべて `app/api/**` で実装。Server Actionsは使用しない（AGENTS.md §1）
- **F3.2はUIレイヤーで完結**: 「安心」フェーズはフロントエンドのみで完結（APIコール不要）。F3.1の生成完了イベントを受け取って即座に表示開始
- **楽観的更新（F3.3）**: マーカーのタップはUIを即座に更新し、DB保存はバックグラウンドで行う。100msレスポンス保証
- **Constitution as Code**: 禁止語（`lib/constitution/banned-words.ts`）・UXシーケンス（`lib/constitution/ux-sequence.ts`）は実行時ではなくCIで検証

## 9. リスクと課題

- **OpenAI API障害・タイムアウト（30秒超過）**：LLM生成不可、ユーザー体験断絶
  - *対策*: 30秒タイムアウト設定＋フレンドリーエラー＋最大3回自動リトライ。リトライ全失敗時はMarkdown+CSS静的フォールバックに自動切替。エラーは `lib/errors/` で一元管理し、クライアントに内部情報を漏洩しない

- **F3.2「安心」フェーズの摩擦化（再訪時）**：ユーザー離脱増加、再訪率悪化
  - *対策*: 再訪時アニメ短縮（2〜3秒）＋テキスト変更（F3.2.8）を必ずPhase 1内に実装。スキップ不可の原則は維持。利用率データからPhase 2で評価

- **レポート満足度4.0/5.0未達**：PMF基準未達、7日以内再訪率30%未達の直結リスク
  - *対策*: F3.4アンケートを初日から稼働させ早期検知。プロンプト改善はえんまさ承認のGate 2プロセスで2週間以内に対応。セクション構成・文体の変更はA/Bテスト候補としてPhase 2で検討

- **F3.3マーカー利用率10%未達**：F4/F5への有効なコンテキスト蓄積不足
  - *対策*: Phase 2で計測。未達なら3スプリント以内に再設計（マーカーボタンの視認性・配置・テキストをえんまさ主導でGate 2改善）

- **AIサブテキスト（F3.2）への禁止語混入・三毒増幅**：ブランド毀損・設計中枢違反
  - *対策*: `lib/constitution/banned-words.ts` によるユニットテストをCIに必須化。えんまさGate 2承認フローを必ず通過させる。「占い」等の禁止語がレポートに1語でも入った場合はビルドを失敗させる

- **F3.5課金ゲートバグ（無料ユーザーが再生成できてしまう）**：LLMコスト流出・ブランド毀損
  - *対策*: Gate 1でStripe `subscription_status` の検証ロジックを必須チェック。再生成APIはIDOR防御・課金状態バリデーションを二重確認

- **Supabase Storage 0.5GB超過**：PNG保存不可
  - *対策*: 90日以上アクセスされていない旧レポートPNGをアーカイブまたは削除するバッチをPhase 1から実装。ストレージ使用量をF9.3ダッシュボードでモニタリング
