1.1 役割と全体像

AI チャット（F4）と統合レポート生成（F3）の中核基盤として、 Vercel AI SDK (ai) + OpenAI Chat Completions API を採用する。

📍 確定経緯：当初仮置きだった「OpenAI Agent Builder」名義から、 2026-05-05 の議論を経て本構成に確定。Dify／OpenAI Assistants API は いずれも不採用（理由はアコーディオン参照）。

用途

  • 5フェーズ共感 AI チャット（F4）
  • 統合レポートのコンテンツ生成（F3）
  • シェアカードのタイプ名生成（F6）

連携方式

  • ai + @ai-sdk/openai パッケージ
  • streamText() + Edge Runtime によるストリーミング応答
  • API キーはサーバー専用（getServerEnv() 経由）
  • フェーズ状態（ChatPhase）は Supabase chat_sessions.phase に永続化。クライアント側にフェーズ状態を持たせない
初回応答3秒以内 → Edge Runtime + ストリーミングが必須。streamText() + Edge Runtime で担保。 要件定義書 §6.3「Vercel AI SDK + OpenAI」/ 議論ログ_AIチャット技術スタック選定 Turn3

1.3 実装イメージ

Edge Runtime での streamText() 呼び出しの最小例。system プロンプトは lib/prompts/ 配下から注入する。

// app/api/chat/route.ts (抜粋・イメージ)
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';
import { getChatPhase1Prompt } from '@/lib/prompts/chat-phase1';

export const runtime = 'edge';

export async function POST(req: Request) {
  const { messages, diagnoses } = await req.json();
  const result = await streamText({
    model: openai('gpt-4o'),
    system: getChatPhase1Prompt({ diagnoses }),
    messages,
  });
  return result.toDataStreamResponse();
}
📌 Key point：フェーズ状態（listening → empathy → exploring → insight → action）は API 側で Supabase chat_sessions.phase から取得・更新する。 クライアントとサーバーで状態を二重管理しない。

1.4 マルチLLM切り替え

Vercel AI SDK の統一コネクターを使えば、プロバイダ切替は import 行を変えるだけで済む。 コスト超過・モデル劣化・障害時の代替手段として確保。 

// プロバイダ切替の例（1行差し替え）
import { openai }    from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { google }    from '@ai-sdk/google';

const result = await streamText({
  model: openai('gpt-4o'),        // ← anthropic('claude-3-5-sonnet') 等に差し替え可能
  messages,
  system: prompt,
});

このコネクター戦略があるため、Dify が提供する「マルチLLM切り替え」機能を別途契約する必要がない。

1.5 選定の経緯（深堀り）

COCOSiL の lib/types/chat-phase.ts は5フェーズ （listening → empathy → exploring → insight → action）を自前の型で管理する設計。 フェーズ遷移ロジックがアプリ側にあり、これは Assistants API の Thread/Run モデルと競合する。

7つのスタートアップ事例のうち、Assistants API を採用して途中で自前実装に戻ったケースが4件。 議論ログ Turn1 / 森田発言

COCOSiL のプロンプトは事業競争力そのもの（Protected Areas Layer 2）。 ワークフロー定義とプロンプトを Dify の GUI 管理に乗せると、以下が壊れる:

  • lib/prompts/ の Git 管理
  • TypeScript 型チェック
  • 禁止語自動検査（F10.3 言語ガバナンス）
D社で Dify 採用を中止させた理由：プロンプトの変更履歴が Git ではなく Dify の DB に入ってしまい、 法令対応でどのバージョンが出荷されたか証明できなくなった。 議論ログ Turn2 / 森田発言

Dify に払うコストで得られる「マルチLLM切り替え」は、Vercel AI SDK で 0円・5行で実現できる（→ §1.4 参照）。

useChat を使いながらサーバー側でも独自セッションを持つ実装パターンが、 パフォーマンス問題を最も多く引き起こす（Vercel 社内調査・川口発言）。

COCOSiL では「フェーズ状態は API + Supabase に一元化」と決めることで、 クライアントは表示と入力に専念、サーバーが真実の所在地という分担を明確化している。

2.2 統合の哲学的根拠 — パンチャ構造（4+1=5）

4体系を統合するのは、機能の足し算ではなく パンチャ構造（4+1=5）の論理的必然。 仏教の「五蘊」=「4つの部分が響き合って、初めて全体（識）が成立する」という構造をプロダクトに翻訳している。

図2-1: パンチャ構造（4+1=5）と4体系のマッピング

📍 引用： 「4つの部分：4つのフレームワークがそれぞれ異なる角度から自己を切り取る。 +1の統合：AIがそれらを統合して1つの立体的な自己像を生成する。 単一フレームでは『ラベル』しか得られない。4視点の統合があって初めて『なぜ自分はこうなのか』の構造的理解（腑落ち）が生まれる。」
— COCOSiL設計中枢 §2.3「4体系統合の哲学的根拠」

2.3 観察軸5軸（Pancha to Five Axes.）

パンチャ構造を実装層に翻訳したのが 観察軸5軸 + メタ層。 正は lib/constitution/observation-axes.ts（Constitution-as-Code）。

仏教用語 コード識別子 日本語表示名
色（rūpa） embodied_pattern 身体・気質パターン
受（vedanā・内的） emotional_response 感情反応パターン
想（saṃjñā） cognitive_style 認知スタイル
行（saṃskāra） motivation_drive 動機エネルギー
受 + 行（対人側） relational_mode 対人モード
識（vijñāna） META_LAYER.self_integration 自己統合（軸ではなく Harvest 結果が表現するメタ層）

設計3原則（Pancha to Five Axes.）

  1. Four Aggregates Expand, Fifth Transcends.　色受想行の4蘊を5軸に展開、識は軸ではなく Harvest 結果のメタ層
  2. Minimal Signature, Rich Expression.　軸のキーワードは識別シグネチャ（3-5語）に限定、表現語彙の豊かさは Deep Research が担う
  3. Priority Resolves Crossings.　軸間の越境概念は layer_priority で主軸を1つ指定して解決
📍 設計改修中（PR #66）: relational_mode は Phase D で 他4軸（embodied/emotional/cognitive/motivation）の相互作用結果として顕現するメタ層に格上げ予定。識（vijñāna）が他4蘊のメタ層であるのと同型構造（4軸 + 1メタ層）。詳細は §2.4 参照。

2.4 ワードツリー統合アルゴリズム — Profiles over Cells.

F3.1 ワードツリー統合は、「4体系 × 5軸 = 20 セル格子」設計（旧 Tree of 4, Harvest 1.）から「幹と枝」モデル（Profiles over Cells）への移行中。 各カテゴリは5軸に分散した特徴ベクトル（プロファイル）を持ち、EMD + 階層クラスタリングで決定論的に統合する。 LLM はナラティブ生成のみを担い、計算ロジックから分離される。

📍 設計改修中（PR #66）: えんまさ実施の Deep Research (2026-05-28) で旧設計の「Procrustean Mapping 問題」が学術的に裏付けられ、現行 20 セル格子から「幹と枝」モデルへの移行計画を策定。Hartmann et al. (2006) の実証研究（N=4,000+ / 11,000+）で「出生月・星座と Big Five・一般知能の統計相関ゼロ」が示されている事実とも整合する。詳細は F3.1 ワードツリー構築 改修計画。

新設計3原則（Profiles, Geometry, Anatta）

  1. Profiles over Cells.　セルではなくプロファイル。各カテゴリは5軸に分散した特徴ベクトルを持つ。例: 水瓶座 = cognitive 0.9 / motivation 0.85 / relational 0.80 / embodied 0.25。「1体系 = 1軸」セル設計の中核削ぎ落とし問題を構造的に解消。
  2. Geometric Fusion, LLM Narration.　幾何で統合、LLM で語る。EMD + 階層クラスタリングは決定論的 TS 関数。LLM はナラティブ層のみ。期待効果: LLM トークン消費 -55% / TTFT 15s → 5s 未満。
  3. Anatta-Aware Output.　無我を意識した出力。「あなたはこういう人です」と固定的に断定する表現を全プロンプトから排除し、「〇〇な傾向が今強め」のような状況依存的・確率的表現に。設計中枢「無明を晴らす」哲学への忠実度向上。

図2-2: 「幹と枝」モデル — 複数体系で合意される中核は太い幹に、特定体系固有の彩りは枝に

計算パイプライン — 決定論層 + LLM 層の分離

  1. Gate 1: カテゴリ抽出（LLM）— ユーザー入力から各体系のカテゴリ（INTP / Aquarius / Cheetah / 土星人 等）を特定
  2. Gate 2: 五蘊多次元ベクトル化（決定論 / 静的データ）— 各カテゴリの5軸 strength + features を lib/data/categories/*.json から取得。LLM 出力ではなく人間が確定したデータ
  3. Gate 3: 距離計算 + 階層クラスタリング（決定論 / TS）— EMD ベース距離行列 + 凝集型クラスタリング（AGNES + Ward 法）で Dendrogram 構築。threshold θ で「幹（中核合意）」と「枝（固有特性）」を分離
  4. Gate 4: 階層的ナラティブ生成（LLM）— 構造化された「幹 / 枝」を入力として、無我を意識した動的表現でレポート生成（温度 0.3-0.5）

3層分類（整合 / 補完 / 矛盾）— 新モデルでの再解釈

旧設計の3層分類「整合 / 補完 / 矛盾」は新設計でも継続。「幹と枝」モデルでは以下のように再解釈される:

  • 整合 = 太い幹（4体系合意の中核特性）
  • 補完 = 中位幹（2-3体系で合意される特性）
  • 矛盾 = 枝同士の競合（異なる体系が反対方向の特性を主張する場合）

F3.1 受け入れ基準 AC-1「4ラベル羅列だけは不合格／統合考察1セクション以上」は Gate 3 の決定論的計算で構造保証される（LLM のプロンプト遵守に頼らない）。

初期設計（PR #61 / #62）では 「4体系 × 5軸 = 20 セル」格子で各セルに特徴語を格納する方針だった（Tree of 4, Harvest 1.）。観察軸5軸を root に据え、その上に4体系の枝を接続し、「太さ = 接続体系数」で収束を検出する設計。

しかし PR #62 初回実走（zodiac × embodied_pattern, Haiku 4.5）で aries の vector が positive → negative に転倒する現象が観測され、調査の結果 Procrustean Mapping 問題（プロクルステース的強制マッピング）が診断された:

  • 各体系のカテゴリは本来複数軸に分散した特徴量を持つ（例: 水瓶座の中核は cognitive / motivation / relational にあり、embodied は副次的）
  • 「1体系 = 1軸」セル設計は各カテゴリの中核を1軸に強制押込 → 副次的側面しか拾えない
  • プロンプト改善では絶対に解消不可能 → 構造的データ設計の見直しが必要

えんまさ実施の Deep Research (2026-05-28) でも、Hartmann et al. (2006) の大規模実証研究（N=4,000+ / 11,000+）が「出生月・星座と Big Five・一般知能の統計相関はゼロ」を示しており、現状設計の限界が学術的に裏付けられた。

旧設計の用語（Tree of 4, Harvest 1. / harvest.representative_keywords 等）は段階的に廃止予定。

ハーバード成人発達研究の「人生の質・健康・幸福度を決定付ける唯一の要因は周囲の人間関係の温かさ」という80年以上の追跡結論を踏まえ、relational_mode は 他4軸（embodied / emotional / cognitive / motivation）の相互作用結果として顕現するメタ層に格上げ予定（Phase D で実装）。

これにより、識（vijñāna）が他4蘊のメタ層であるのと同じ構造で、relational_mode が他4軸のメタ層となる。設計中枢のパンチャ構造解釈もより精緻化される。

🟢 Positive Test（引用率 + 多様性）

  • 「幹」「枝」両方からの特徴語引用が 最低3語以上 各セクションに含まれる
  • 全体での引用率は 40〜60% を目安
  • vector / confidence の3値全出現と σ ≥ 0.10 を Gate 3 で機械保証

🔴 Negative Test（ハルシネーション + バーナム効果対策）

  • カテゴリプロファイルに存在しない体系特徴語の混入率 ≤5%
  • 「あなたはこういう人です」型の固定断定構文を lib/constitution/banned-output-patterns.ts（Phase D で新設）で機械検出 → 検出率 100%
  • 双方向バイアス対策: negative 見落とし（過小評価）と positive 過小評価（脆弱性記述に引きずられた negative 過判定）を Critique LLM で同等に疑う

検証ツール: promptfoo + ヒラメ・えんまさ・みさきさんによる「近い/遠い」直感投票 10 ペア（Phase E で threshold θ 較正）

🔴 B-1: 並列羅列への退化（最優先・タスクの存在意義の否定）

「あなたは蟹座で〜、ENFPで〜、ペガサスで〜」と各体系を順番に説明するレポートが出る状態。「幹と枝」の階層構造が崩壊。

🔴 B-2: ハルシネーション（ステレオタイプ汚染）

カテゴリプロファイル外の俗説特徴語が混入。Negative Test で混入率 >5%。

🔴 B-3: 固定断定構文の混入（無我抵触）

「あなたは〇〇な人です」「〇〇タイプです」と固定的に断定する表現が出力に混入。banned-output-patterns.ts で検出されたら自動 reject。

🔴 B-4: バーナム効果（中和化された平坦な記述）

階層クラスタリングの distance threshold が緩すぎて、全カテゴリで似たような「太い幹」が抽出され、誰にでも当てはまる薄い中核ばかりが残る状態。Phase E のゴールデンサンプル較正で防止。

Phase期間内容
A5日データ層再構築（lib/data/categories/ 新設・100カテゴリ JSON）
B5日計算エンジン実装（distance / fusion-engine / trunk-branch）
C5日パイプライン改修（カテゴリ単位 CLI、Schema 差替）

PR #62 の扱い: ObservationTreeDataSchema は本改修で全面廃止対象のため、クローズ判断を推奨。流用資産（AI Gateway 認証・smoke test・パイプライン構造）は Phase C で取り込む。

3.3 F3「安心」フェーズ — 設計三原則

F3 統合レポートの核心は、レポート本体表示前に挟まれる「安心」フェーズ（F3.2）。 LLM 生成中の待ち時間（最大15秒）を、ユーザーの認知シフト時間に変換する設計。

  1. Zero-Effort Reassurance
    ユーザーにコストを払わせない。受動的に体験する。
  2. Active → Receptive Handoff
    F1.3（共感: 語る）から F3.2（安心: 受け取る）へのモード切替。
  3. De-judging through Metaphor
    「結果 = 評価」を「結果 = 地図」に認知シフト。
具体仕様
  • 呼吸アニメーション 4〜8秒
  • テキスト：「あなたの結果が揃いました。読む前に、ひとつだけ。」（60字以内）
  • AI サブテキスト：承認・脱判定化・招待の3要素（100字以内、えんまさ設計）
  • CTA「読んでみる→」（Thumb Zone 内）
  • CTA タップまたは 15秒経過後にレポート本体に遷移

文字レイヤーは Vercel OG が 100% 担保する。gpt-image-2 には文字を持たせない。 フォント崩れ・誤字混入のリスクを排除するため。

フェーズ3以降: gpt-image-2（背景・アイコン専用）

  • 各体系の象徴背景・アイコン画像の生成のみ。文字は担当しない
  • 連携方式: Inngest JobQueue 経由で非同期生成 → Sharp で Vercel OG の文字レイヤーと合成
  • コスト: ~$525/月（Batch API・quality=high・月5,000枚の場合）
  • PoC 条件: フェーズ2完了後に quality=low で品質検証。品質不足なら Vercel OG のみで継続
📌 確定経緯：Gamma API（月額約2万円）からの移行を 2026-05-07 に確定。 根拠は 議論ログ_imager2アーキ選定.md。

3.5 フォールバック設計

レポート生成は複数の独立した障害点を持つため、各段でフォールバックを用意する。

失敗ポイント フォールバック UX 影響
LLM 生成失敗（タイムアウト 30秒） 「少し時間がかかっています」表示 + リトライ導線 低（明示的待機）
Vercel OG 生成失敗 Markdown + CSS 静的レポート 低（読める形は保証）
gpt-image-2（フェーズ3）失敗 Vercel OG のみで表示継続（背景画像なし） 極小（装飾レイヤーのみ欠ける）
レポート再生成（F3.5）— 課金未加入 「有料プランで月1回再生成できます」誘導 適切な動線

ポイント: 外部 API（gpt-image-2）に「読めるかどうか」の責任を持たせない。 文字は Vercel OG（サーバーサイド）で 100% 担保することで、外部 API 障害時もレポートは届く。

3.6 レポート本体 → F3.3 / F3.4 / F3.5

  3. 再生成ボタン（前回生成から30日経過後に有効化: F3.5・課金ユーザーのみ）

  • F3.4 満足度 ≥4.0
  • 7日内再訪率 ≥30%（設計中枢 PMF 基準）
