1.1 役割と全体像

AI チャット（F4）と統合レポート生成（F3）の中核基盤として、 Vercel AI SDK (ai) + OpenAI Chat Completions API を採用する。

📍 確定経緯：当初仮置きだった「OpenAI Agent Builder」名義から、 2026-05-05 の議論を経て本構成に確定。Dify／OpenAI Assistants API は いずれも不採用（理由はアコーディオン参照）。

用途

  • 5フェーズ共感 AI チャット（F4）
  • 統合レポートのコンテンツ生成（F3）
  • シェアカードのタイプ名生成（F6）

連携方式

  • ai + @ai-sdk/openai パッケージ
  • streamText() + Edge Runtime によるストリーミング応答
  • API キーはサーバー専用（getServerEnv() 経由）
  • フェーズ状態（ChatPhase）は Supabase chat_sessions.phase に永続化。クライアント側にフェーズ状態を持たせない
初回応答3秒以内 → Edge Runtime + ストリーミングが必須。streamText() + Edge Runtime で担保。 要件定義書 §6.3「Vercel AI SDK + OpenAI」/ 議論ログ_AIチャット技術スタック選定 Turn3

1.3 実装イメージ

Edge Runtime での streamText() 呼び出しの最小例。system プロンプトは lib/prompts/ 配下から注入する。

// app/api/chat/route.ts (抜粋・イメージ)
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';
import { getChatPhase1Prompt } from '@/lib/prompts/chat-phase1';

export const runtime = 'edge';

export async function POST(req: Request) {
  const { messages, diagnoses } = await req.json();
  const result = await streamText({
    model: openai('gpt-4o'),
    system: getChatPhase1Prompt({ diagnoses }),
    messages,
  });
  return result.toDataStreamResponse();
}
📌 Key point：フェーズ状態（listening → empathy → exploring → insight → action）は API 側で Supabase chat_sessions.phase から取得・更新する。 クライアントとサーバーで状態を二重管理しない。

1.4 マルチLLM切り替え

Vercel AI SDK の統一コネクターを使えば、プロバイダ切替は import 行を変えるだけで済む。 コスト超過・モデル劣化・障害時の代替手段として確保。 

// プロバイダ切替の例（1行差し替え）
import { openai }    from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { google }    from '@ai-sdk/google';

const result = await streamText({
  model: openai('gpt-4o'),        // ← anthropic('claude-3-5-sonnet') 等に差し替え可能
  messages,
  system: prompt,
});

このコネクター戦略があるため、Dify が提供する「マルチLLM切り替え」機能を別途契約する必要がない。

1.5 選定の経緯（深堀り）

COCOSiL の lib/types/chat-phase.ts は5フェーズ （listening → empathy → exploring → insight → action）を自前の型で管理する設計。 フェーズ遷移ロジックがアプリ側にあり、これは Assistants API の Thread/Run モデルと競合する。

7つのスタートアップ事例のうち、Assistants API を採用して途中で自前実装に戻ったケースが4件。 議論ログ Turn1 / 森田発言

COCOSiL のプロンプトは事業競争力そのもの（Protected Areas Layer 2）。 ワークフロー定義とプロンプトを Dify の GUI 管理に乗せると、以下が壊れる:

  • lib/prompts/ の Git 管理
  • TypeScript 型チェック
  • 禁止語自動検査（F10.3 言語ガバナンス）
D社で Dify 採用を中止させた理由：プロンプトの変更履歴が Git ではなく Dify の DB に入ってしまい、 法令対応でどのバージョンが出荷されたか証明できなくなった。 議論ログ Turn2 / 森田発言

Dify に払うコストで得られる「マルチLLM切り替え」は、Vercel AI SDK で 0円・5行で実現できる（→ §1.4 参照）。

useChat を使いながらサーバー側でも独自セッションを持つ実装パターンが、 パフォーマンス問題を最も多く引き起こす（Vercel 社内調査・川口発言）。

COCOSiL では「フェーズ状態は API + Supabase に一元化」と決めることで、 クライアントは表示と入力に専念、サーバーが真実の所在地という分担を明確化している。

2.2 統合の哲学的根拠 — マクロは「パンチャ構造（4+1=5）」、ミクロは「3段階モデル」

4体系を統合するのは、機能の足し算ではなく パンチャ構造（4+1=5）の論理的必然。 仏教の「五蘊」=「4つの部分が響き合って、初めて全体（識）が成立する」という構造をプロダクトに翻訳している。
ただし マクロの哲学（4視点 + 1統合）は保ちつつ、ミクロの実装は「3段階モデル」（核 → 振る舞い → 時期の出方）に再設計 した（2026-05-28 議論で確定）。

図2-1: マクロのパンチャ構造（左）から、ミクロの3段階モデル（右）への翻訳

📍 引用（マクロは維持）： 「4つの部分：4つのフレームワークがそれぞれ異なる角度から自己を切り取る。 +1の統合：AIがそれらを統合して1つの立体的な自己像を生成する。 単一フレームでは『ラベル』しか得られない。4視点の統合があって初めて『なぜ自分はこうなのか』の構造的理解（腑落ち）が生まれる。」
— COCOSiL設計中枢 §2.3「4体系統合の哲学的根拠」

2.3 3段階モデル — 核 → 振る舞い → 時期の出方

パンチャ構造のミクロ実装は 3段階モデル。一生変わらない ① 心の核 の上に、 生まれつきだが少し変わる ② 振る舞いスタイル が乗り、さらに時期で変わる ③ 今の時期の出方 が外側を覆う。

📍 確定経緯： 現行 F3.1（観察軸5軸 × 4体系 = 20セル）は Procrustean Mapping 問題（軸先行射影で 各体系の特徴の 60-80% を捨てている）を抱えていた。2026-05-28 の議論を経て、各体系の伝統的大分類を尊重する 「幹と枝」モデル + 3段階レイヤーへ移行した。観察軸5軸は降格して「枝の分類タグ」として再利用する（消さない）。
— 議論ログ_4体系統合メソッド幹と枝モデル Turn 6 / 議論ログ_N_M確率モデルのhelp反映 Turn 1

設計4原則（3段階モデル × N:M 確率）

  1. Three-Layer Architecture, Tensor-Decomposed.　3段階モデルはテンソル分解構造で実装する（Layer 1 = 4元素、Layer 2 = 8スタイル、Layer 3 = 4季節）
  2. Probability is Truth, Hallucination is Drift.　ユーザーの確率分布が唯一の真実。LLM 生成文章は分布として再投影し、KL ダイバージェンスで逸脱を機械判定する
  3. Static Constitution, Dynamic Modulation.　静的マトリクス S（8×4）は Constitution として不変。動的変調 Q(t) はアダマール積で合成、L1 正規化で確率分布の保存則を維持
  4. Hierarchical Alpha, Cited Provenance.　距離関数の α は層遷移で変える（Layer 1↔2 で 0.7、Layer 2↔3 で 0.3）。各セルには Greene/Beebe/Keirsey の出典タグを付与

2.4 N:M 確率マッピング — Static × Dynamic + Hierarchical α + KL Eval

3段階モデルの層と層を繋ぐ計算は、2つの数式に集約される。 静的マトリクス S（生まれ持った構造）と 動的変調 Q(t)（今の時期）の アダマール積を L1 正規化して、現在の確率分布 P(t) を得る。

📐 核となる2式 
Static mapping :  P_static = S ∈ [0, 1]^(8×4)  with rowSum(S) = 1
Dynamic state  :  P(t) = normalize_L1( S ⊙ Q(t) )

S は 8行（Layer 2 の8スタイル）× 4列（Layer 1 の4元素）の 行確率行列。 各行の合計が厳密に 1.00、各要素が非負。
Q(t) は同形の動的変調行列（季節別）。⊙ はアダマール積（要素ごとの積）、 normalize_L1 は行ごとの L1 正規化（合計を 1 に戻す）。

静的マトリクス S（8×4）のサンプル — NF（Idealist）行

学術的根拠は Keirsey (1998) Please Understand Me II, Greene (1984) The Astrology of Fate, Beebe (2017) Energies and Patterns in Psychological Type。 全8行は lib/constitution/three-layer-model.ts に LAYER2_TO_LAYER1_MAPPING 等の不変定数として格納（コミット f821408 で実装済み）。

Layer 2 スタイル Fire（火 / 直観） Earth（土 / 感覚） Air（風 / 思考） Water（水 / 感情） 合計 主要根拠（出典タグ）
NF (Idealist) 0.25 0.05 0.10 0.60 1.00 Keirsey 1998 / Greene 1984 / Beebe 2017
※ 他の 7 行（SP/SJ/NT/太陽/地球/満月/新月）は Q4 Deep Research §5.1 を参照。各セルに derivation_source: [keirsey, greene, beebe, ...] 出典タグを付与。

ユーザー表示（主要成分強調）

確率値はすべて出すが、エントロピー閾値 20% で 主成分・副成分・脇役 に3階級化する。 NF の場合：水（0.60） + 副成分 火（0.25） + 脇役 風（0.10）・土（0.05）。 ラベル単体だと違和感がある副成分（例：INFP に「火25%」）は、出典タグから自動生成された出自説明 （例：「Keirsey NF の Apollonian 由来 + 蠍座の固定宮由来」）を併記してハルシネーション感を消す。

階層別 α — 深層は Rule 重視、表層は Embedding 重視

遷移α（Rule 重み）1-α（Embedding 重み）根拠
Layer 1 ↔ Layer 20.70.3象徴体系の不変対応を尊重、深層は Greene/Beebe の理論駆動が優位
Layer 2 ↔ Layer 30.30.7言語表現の揺らぎや感情ニュアンスに柔軟、表層は文脈駆動が優位

距離関数は distance(A, B) = α × RuleDistance + (1-α) × EmbeddingDistance。 一律 α = 0.5 という前回案は捨て、「深層ほど理論駆動、表層ほど文脈駆動」という認知階層性原則に置き換えた。 出典: Q4 §4.3 / Friston 自由エネルギー原理。

🟢 Positive Test（出典付き引用）

  • 各レポートセクションで derivation_source から 最低 1 件の出典タグ を引用
  • 主成分（>20%）の元素について、その出自（Keirsey/Greene/Beebe 等）を語る

🔴 Negative Test（ハルシネーションを数式で検出）

  • LLM 生成文章の 4 元素キーワード頻度分布 F_norm を計算
  • ユーザー確率分布 P_user との KL ダイバージェンス ≤ 0.3
  • 例：INFP（水60%）のレポートで火の話ばかり書いていれば KL 値が跳ね上がり、機械的に検出

🔴 B-1: 並列羅列への退化（最優先・タスクの存在意義の否定）

「あなたは蟹座で〜、ENFPで〜、ペガサスで〜」と各体系を順番に説明するレポートが出る状態。3段階モデルの「核 → 振る舞い → 時期」構造が消える。

🔴 B-2: ハルシネーション（KL ダイバージェンス > 0.3）

ユーザーの確率分布から逸脱した俗説特徴語が混入（「蟹座は家庭的だから尽くす女性」「ENFP は飽きっぽい」等）。KL Eval で機械的に検出。

🔴 B-3: 行確率保存則の破綻

S または Q(t) の行合計が 1.0 から逸脱、または負値が混入。Vitest 不変条件で常時検出。

🔴 B-4: 同一入力で異なる harvest（再現性破綻）

同じユーザー入力に対して、確率分布が実行ごとに異なる。Vitest unit test で検出。

3.3 F3「安心」フェーズ — 設計三原則

F3 統合レポートの核心は、レポート本体表示前に挟まれる「安心」フェーズ（F3.2）。 LLM 生成中の待ち時間（最大15秒）を、ユーザーの認知シフト時間に変換する設計。

  1. Zero-Effort Reassurance
    ユーザーにコストを払わせない。受動的に体験する。
  2. Active → Receptive Handoff
    F1.3（共感: 語る）から F3.2（安心: 受け取る）へのモード切替。
  3. De-judging through Metaphor
    「結果 = 評価」を「結果 = 地図」に認知シフト。
具体仕様
  • 呼吸アニメーション 4〜8秒
  • テキスト：「あなたの結果が揃いました。読む前に、ひとつだけ。」（60字以内）
  • AI サブテキスト：承認・脱判定化・招待の3要素（100字以内、えんまさ設計）
  • CTA「読んでみる→」（Thumb Zone 内）
  • CTA タップまたは 15秒経過後にレポート本体に遷移
— 要件定義書 §4.3 業務フロー / F3.2

3.4 整形パイプライン — Vercel OG / gpt-image-2

フェーズ1〜2: Vercel OG (Satori)

  • LLM 生成のレポートコンテンツを React コンポーネントでリッチ画像に変換
  • 実装: app/api/reports/generate/route.ts から @vercel/og を呼び出し
  • 同期・即時生成（タイムアウトなし）
  • 出力: PNG 1024×1792（縦長スマホ向け）→ Supabase Storage user-reports バケットに永続化
  • コスト: ~¥0〜1,500/月（Vercel Function 実行コストのみ）
📍 設計制約：Text is Sacred
文字レイヤーは Vercel OG が 100% 担保する。gpt-image-2 には文字を持たせない。 フォント崩れ・誤字混入のリスクを排除するため。

フェーズ3以降: gpt-image-2（背景・アイコン専用）

  • 各体系の象徴背景・アイコン画像の生成のみ。文字は担当しない
  • 連携方式: Inngest JobQueue 経由で非同期生成 → Sharp で Vercel OG の文字レイヤーと合成
  • コスト: ~$525/月（Batch API・quality=high・月5,000枚の場合）
  • PoC 条件: フェーズ2完了後に quality=low で品質検証。品質不足なら Vercel OG のみで継続
📌 確定経緯：Gamma API（月額約2万円）からの移行を 2026-05-07 に確定。 根拠は 議論ログ_imager2アーキ選定.md。

3.5 フォールバック設計

レポート生成は複数の独立した障害点を持つため、各段でフォールバックを用意する。

失敗ポイント フォールバック UX 影響
LLM 生成失敗（タイムアウト 30秒） 「少し時間がかかっています」表示 + リトライ導線 低（明示的待機）
Vercel OG 生成失敗 Markdown + CSS 静的レポート 低（読める形は保証）
gpt-image-2（フェーズ3）失敗 Vercel OG のみで表示継続（背景画像なし） 極小（装飾レイヤーのみ欠ける）
レポート再生成（F3.5）— 課金未加入 「有料プランで月1回再生成できます」誘導 適切な動線

ポイント: 外部 API（gpt-image-2）に「読めるかどうか」の責任を持たせない。 文字は Vercel OG（サーバーサイド）で 100% 担保することで、外部 API 障害時もレポートは届く。

3.6 レポート本体 → F3.3 / F3.4 / F3.5

  1. レポート本体表示後、各セクションに「しっくりきた」マーカーボタン（F3.3）— タップで記録
  2. レポート末尾に満足度アンケート（5段階+自由記述: F3.4）
  3. 再生成ボタン（前回生成から30日経過後に有効化: F3.5・課金ユーザーのみ）
📍 KPI / PMF 基準
  • F3.3 マーカー利用率 各セクション ≥10%
  • F3.4 満足度 ≥4.0
  • 7日内再訪率 ≥30%（設計中枢 PMF 基準）
