F3 統合レポート — 実装マニュアル

4体系診断データを「1つの立体的な自己像」に統合し、文字崩れゼロの縦長レポートとして即時生成する。 本マニュアルは app/api/** 担当（ヒラメ）が F3.1〜F3.5 を実装するための手引き。 要件定義書・F3システム要件・TSKファイル・確定済みプロンプトからの引用で構成。

1.1 F3 とは

F2で収集した4体系（星座・60type動物・六星・MBTI）を OpenAI が統合し、 パンチャ構造（4+1=5）の論理で「なぜ自分はこうなのか」が構造として腑落ちするレポートを生成する。 単なるラベルの羅列ではなく 統合考察 が核。

📍 非交渉のUXシーケンス：レポート表示の直前に必ず「安心」フェーズ（F3.2）が挟まる。 共感 → 安心 → 分析 → 行動 の順序はコードレベルで保証する（F3.2 はスキップ不可）。

1.2 生成パイプライン

図1: F3.1 レポート生成パイプライン（TSK-API-002）

文字レイヤーは Vercel OG が担保するため、OG生成失敗時の Markdown+CSS フォールバックでも文字崩れは起きない。 gpt-image-2（背景・アイコン）は Phase 3 以降の追加で、Phase 1〜2 は依存ゼロ。 F3システム要件 §技術スタック / 議論ログ_imager2アーキ選定

1.3 担当境界（Protected Areas）

  • Layer 3（AI委任OK・ヒラメ担当）：app/api/** のルート実装。PRレビュー前提
  • Layer 2（えんまさ承認必須）：lib/prompts/**（プロンプト）/ lib/data/**（4体系ナレッジ）。呼び出すのはOK、内容変更は Gate 2
  • Layer 1（hookで自動ブロック・手動のみ）：supabase/migrations/** / .env* / RLS無効化系SQL
プロンプト本体（integrated-report.ts）は確定済み・テスト緑（PR #68）。ヒラメは import して使うだけで、中身を書き換える場合は えんまさの Gate 2 が必要。

2.1 TSK-API-002 実装ステップ

  1. Zod（zod/v4）スキーマで入力（4体系データ・user_id）を検証
  2. Clerk JWT 検証 → supabase.auth.getUser() でユーザー特定（request.headers 直読み禁止）
  3. OpenAI（30秒タイムアウト）でレポート本文を JSON 生成。失敗時は Markdown+CSS フォールバック
  4. 生成JSONを og-image.tsx に流し込み @vercel/og で 1024×1792 PNG 化
  5. Supabase Storage user-reports に ${user_id}/${uuid}.png で保存
  6. RLS policy で user_id = auth.uid() を Storage objects に適用
📍 Server Actions 不使用（厳格ルール）：全ビジネスロジックは app/api/** の Route Handler。 "use server" 関数にDB書き込み・診断計算・認証チェックを置かない。

想定ファイル構成（TSK-API-002）

app/api/reports/
  └── generate/route.ts          # POST /api/reports/generate
lib/reports/
  ├── og-image.tsx               # Vercel OG (Satori) Reactコンポーネント
  ├── markdown-fallback.ts       # Markdown+CSS 静的フォールバック
  ├── llm.ts                     # OpenAI レポート生成（30秒タイムアウト）

supabase/migrations/
  └── (RLS policy: storage.objects user-reports)

2.2 プロンプト連携（最重要）

レポート本文プロンプトは lib/prompts/integrated-report.ts（確定済み）から2つの関数で組み立てる。 ヒラメはこれを呼び出して OpenAI に渡すだけ。

export役割
resolveIntegratedReportSystemPrompt(hasName)system プロンプトを返す。hasName で呼称トーン（「さん」付け／「あなた」）を分岐
buildIntegratedReportUserPrompt(input)4体系データ＋呼び名を流し込んだ user メッセージを返す
REPORT_SECTION_IDS出力JSONのキー（=セクション）。F3.3マーカーもこのIDを参照
REPORT_SECTION_CHAR_LIMITS各セクションの文字数上限（OGレイアウト崩壊防止）

呼び出しイメージ

// lib/reports/llm.ts（抜粋・イメージ）
import {
  resolveIntegratedReportSystemPrompt,
  buildIntegratedReportUserPrompt,
} from '@/lib/prompts/integrated-report';

const hasName = Boolean(displayName);
const system = resolveIntegratedReportSystemPrompt(hasName);
const user = buildIntegratedReportUserPrompt({
  displayName,                                  // null なら「あなた」にフォールバック
  zodiac:  { label: '蟹座' },
  animal:  { label: '母性豊かな子守熊' },        // 60type character ラベル（D10）
  sixStar: { label: '土星人＋' },
  mbti:    { label: 'INFJ' },
  // ② TSK-DATA 整備後は各項目に description を渡す:
  // zodiac: { label: '蟹座', description: '…詳細説明文…' }
});
// → OpenAI に system / user を渡し、JSON モードで取得

出力JSONの構造（5セクション + キャッチフレーズ）

{
  "catchphrase":     "一言の命名（20字程度・OG見出し用）",
  "opening":         "導入（地図メタファー）",
  "four_lights":     "4体系それぞれの短い読み取り",
  "integration":     "統合考察＝核（4体系横断・AC-1）",
  "relational_hint": "大切な人との関係ヒント（AC-2）",
  "closing":         "結び（次アクションへの招待）"
}
📍 ② 詳細説明文の注入：現状プロンプトは4体系の ラベルだけを渡す。 各タイプの詳細説明文（TSK-DATA-XXX）が揃ったら SystemProfile.description に流し込む。 未整備でもラベルのみで動作する（フォールバック設計済み）。

2.3 LLM 出力は単段で信用しない

生成 → 抽出 → Schema検証 → （必要なら）再生成、の順で扱う。JSON をそのまま PNG 化しない。

  1. OpenAI を JSON モードで呼ぶ
  2. JSON.parse 後、REPORT_SECTION_IDS の全キーが揃うか Zod で検証
  3. 各セクションが REPORT_SECTION_CHAR_LIMITS を超えていないかチェック（超過は clamp or 再生成）
  4. 禁止語チェック（findBannedWords()）を出力にも通す
  5. 検証通過後に og-image.tsx へ
生成→抽出→Schema→Critique→人間サンプリングの多段パイプラインが標準。単段生成の JSON を信頼しない。 プロジェクト方針（LLM JSON パイプライン）

2.4 フォールバック2層

失敗箇所挙動
OpenAI タイムアウト（30s超）/ エラーフレンドリーエラー＋リトライ導線。エラーオブジェクトをそのままクライアントに返さない
Vercel OG 生成失敗Markdown+CSS 静的レポートへ即時切替。ユーザーに生成失敗を悟らせない

2.5 F3.3 マーカー / F3.4 アンケート（TSK-API-008）

  • F3.3：セクション単位（REPORT_SECTION_IDS）でマーク記録。1タップで記録・解除（可逆）。F4.3/F5.3から参照可能にする
  • F3.4：5段階スコア＋自由記述（空でも送信可）を記録。F9.3 KPIダッシュボード（満足度4.0目標）に集計
  • 両テーブルとも user_id = auth.uid() の RLS を必ず適用（Gate 1）
未マーク時に「0件です」等の 否定形を出さない（AC-3・設計中枢 原則②）。これはUI側の責務だがAPIの返却設計でも残件数を強調しない。

2.6 F3.5 再生成（TSK-API-009・Phase 3）

  • 課金プラン限定（無料は有料誘導）・月1回上限・前回から30日ゲート
  • 処理順：課金状態検証 → 月次枠消費 → 生成 → 保存
  • 蓄積データ（F4チャット・F3.3マーカー・F5記録）をプロンプトに注入（D3）。乏しい場合のフォールバックを用意
  • F3.1の生成フロー（LLM→OG→Storage）を再利用

3.1 Gate 1（ヒラメ）— 全PR必須

項目観点
IDOR防御user_id = auth.uid() が全CRUD操作のRLSポリシーに存在するか
JWT連携Clerk JWTが supabase.auth.getUser() 経由（request.headers 直読み禁止）
型安全の境界APIルート入力値が Zod スキーマで検証されているか
N+1・漏洩クエリループ内Supabase呼び出しなし / select('*') で不要カラム露出なし
エラー境界Supabaseエラーをそのままクライアントに返していないか
認証・DB migration・API route を変更するPRは /security-sensitive-change-review を必ず通す。

3.2 非機能要件（目標値）

項目目標値

3.3 壊れ方3パターン（/start-task 時に宣言）

診断計算・プロンプト組み立ての確定性。Vitest unit test で確認。入力が同じなら system/user プロンプトも同一になることを保証する。

Storage保存・マーカー記録が auth.uid() 境界で正しく読み書きできるか。プレビューURL＋手動ログ確認。

えんまさによるプレビューURL手動確認。共感→安心→分析→行動の順序、年齢非表示、呼称トーンなどを目視。

3.4 実装時の落とし穴チェック

  • 年齢非表示（D9）：本文・OG・シェアカードに年齢を出さない。生年月日はフッターの計算根拠表示のみ。シェアカード（F6）には生年月日も出さない
  • 60type characterラベル（D10）：ユーザー向けは character（例「リーダーとなるゾウ」）。baseAnimal 単体は内部参照のみ
  • display_name モデレーション（D8）：差別語・他人名・絵文字攻撃を lib/constitution/ のルールで遮断。OG描画前に再チェック、検知時は「あなた」に置換。20文字超は clamp
  • 禁止語0%：占い/鑑定/運勢/当たる/霊感/霊視。lib/constitution/banned-words.ts が唯一の正。出力にも findBannedWords() を通す
  • env var：@/lib/env の getServerEnv() 経由。process.env.XXX 直読み禁止
  • パッケージ：pnpm のみ。@/* はプロジェクトルートにマップ（src/ は無い）

3.5 検証コマンド & 完了の定義

pnpm typecheck   # tsc --noEmit
pnpm lint        # ESLint
pnpm build       # Next.js build
pnpm exec vitest run   # 単体テスト
機能完了 = 型チェック通過（機械）＋ ビルド成功（機械）＋ 動作確認済み（えんまさ）
「ビルドが通ったから完了」は禁止。3条件が揃うまで main マージ不可。
